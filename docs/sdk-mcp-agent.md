Для агента важнее не просто «выполнить команду», а иметь цикл:

```text
прочитать состояние → принять решение → изменить модель → проверить результат
```

Текущий `kompas_bridge.exe` — хороший технический прототип, но для MCP его нужно сделать постоянно работающим процессом с одним STA COM-потоком и одним подключением к КОМПАСу.

```text
AI-агент
  → MCP tools
  → Python kompas_mcp
  → Named Pipe / JSON
  → постоянный kompas_bridge
  → один COM-сеанс API5/API7
  → открытый КОМПАС-3D
```

Ключевой момент: bridge не должен завершаться после одной команды. Он должен жить, хранить COM-сессию, выполнять запросы строго последовательно и поддерживать внутренние ссылки на документы и элементы.

Для начала я бы реализовал не сотню микрокоманд, а около 12 полезных MCP-инструментов.

```text
kompas_status
kompas_documents_list
kompas_document_create_3d
kompas_document_open
kompas_document_activate
kompas_document_save_as
kompas_document_close
kompas_model_state
kompas_model_apply
kompas_undo
kompas_redo
kompas_view_screenshot
```

Самый важный здесь — `kompas_model_apply`. Он принимает декларативный набор действий, а не произвольный C++ или Python-код:

```json
{
  "document_id": "active",
  "operations": [
    {
      "op": "create_sketch",
      "id": "base_sketch",
      "plane": "xoy"
    },
    {
      "op": "add_rectangle",
      "sketch_id": "base_sketch",
      "center": [0, 0],
      "width_mm": 50,
      "height_mm": 50
    },
    {
      "op": "extrude",
      "id": "cube_feature",
      "sketch_id": "base_sketch",
      "depth_mm": 50
    }
  ]
}
```

Ответ должен содержать не только `ok`, но и идентификаторы созданных объектов:

```json
{
  "ok": true,
  "document_id": "doc_1",
  "created": {
    "base_sketch": "entity_42",
    "cube_feature": "entity_43"
  }
}
```

Тогда агент сможет написать: «Сделай куб 50 мм, затем увеличь высоту до 80 мм». Он сначала создаёт feature с понятным `id`, а затем отправляет:

```json
{
  "document_id": "doc_1",
  "operations": [
    {
      "op": "update_extrusion",
      "feature_id": "cube_feature",
      "depth_mm": 80
    }
  ]
}
```

Нужны четыре уровня API.

1. Управление приложением и документами:

- найти запущенный КОМПАС или запустить новый;
- получить список открытых документов;
- открыть, создать, активировать, сохранить, закрыть документ;
- определить активный документ и его тип;
- не создавать новый экземпляр КОМПАСа, если пользователь уже работает в существующем.

Для этого factory стоит развить: сначала пытаться подключиться к активному COM-объекту через ROT, и только затем создавать новый экземпляр.

2. Наблюдение за моделью:

- дерево модели: детали, эскизы, операции;
- параметры выбранного feature;
- имя, тип и расположение элемента;
- текущая плоскость, выбранные объекты, единицы измерения;
- снимок экрана или экспорт превью.

Без `model_state` агент будет действовать вслепую. После каждой важной операции он должен видеть, что реально получилось.

3. Изменение геометрии:

- создание эскиза на базовой или выбранной плоскости;
- линии, окружности, прямоугольники, контуры;
- размеры и геометрические ограничения;
- выдавливание, вырезание, вращение;
- отверстие, скругление, фаска, массив;
- изменение параметров уже созданных операций;
- удаление и подавление feature.

4. Безопасность и управляемость:

- `undo`/`redo`;
- транзакция: группа операций либо завершается целиком, либо откатывается;
- запрет опасных операций без явного подтверждения: закрыть несохранённый файл, перезаписать файл, удалить feature;
- отдельный режим «только чтение»;
- журнал действий агента в JSON.

Для ссылок на объекты лучше не заставлять агента использовать сырые COM-указатели. Bridge должен выдавать свои `document_id` и `entity_id`, а сам хранить соответствие. Для долгоживущих объектов полезно дополнительно задавать им имена или пользовательские атрибуты в модели — тогда элемент можно будет найти и после повторного открытия файла.

Практичный план развития:

1. Постоянный bridge с Named Pipe и JSON-протоколом.
2. Подключение к уже открытому КОМПАСу и `documents_list`.
3. `model_state` и скриншот активного документа.
4. `model_apply` с тремя операциями: `create_sketch`, `add_rectangle`, `extrude`.
5. Обновление параметров: `update_extrusion`.
6. Открытие, сохранение и закрытие документов.
7. Расширение 3D-операций и затем 2D-чертежей.

Я бы следующим шагом делал не ещё одну геометрическую команду, а persistent bridge + `documents_list`/`model_state`. Это даст агенту «глаза» и постоянный контекст, без которых автоматизация быстро становится ненадёжной.
