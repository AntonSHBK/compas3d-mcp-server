# Внутренний протокол Python ↔ C++ bridge

## Область применения

Это целевой контракт между `kompas_bridge_transport` и долгоживущим
`kompas_bridge`. Он не является MCP-протоколом. Кодек версии 1 и framing
реализованы в `kompas_bridge_protocol` и тестируются без КОМПАСа. Старые
демонстрационные CLI-команды удалены. Рабочий транспорт — Windows Named Pipe;
stdio сохранён только для разработки и ручной диагностики.

Протокол предоставляет закрытый перечень низкоуровневых методов. Вызов
произвольного C++, Python, COM-метода или фрагмента KsAPI через запрос
не допускается. Составные CAD-сценарии и семантический выбор элементов
принадлежат `kompas_core`.

## Сообщения версии 1

Каждый запрос содержит версию протокола, идентификатор, имя метода и объект
параметров:

```json
{
  "protocol_version": 1,
  "id": "req-42",
  "method": "document.get_active",
  "params": {}
}
```

Успешный ответ повторяет `id` и содержит объект `result`:

```json
{
  "protocol_version": 1,
  "id": "req-42",
  "ok": true,
  "result": {
    "document_id": "doc-1",
    "document_type": "part_3d",
    "file_path": null
  }
}
```

Ответ с ошибкой содержит объект `error` вместо `result`:

```json
{
  "protocol_version": 1,
  "id": "req-42",
  "ok": false,
  "error": {
    "code": "no_active_document",
    "message": "No active document is available.",
    "details": {}
  }
}
```

`id` — непустая строка, уникальная среди одновременно ожидающих запросов
одного клиента (не более 128 байт UTF-8). Повторное использование `id` после
ответа допустимо. Учёт ожидающих `id` — ответственность транспорта; кодек
проверяет только тип, непустоту и длину. Bridge возвращает её без изменения;
при ошибке чтения JSON,
когда `id` определить нельзя, возвращает `id: null`. `method` — строка из
зарегистрированного списка. `params` и `result` — JSON-объекты; `details` —
JSON-объект с диагностическим контекстом без внутренних COM-указателей.
`ok` — булево значение. Неизвестная версия или метод возвращают ошибку,
а не вызывают произвольную функцию.

Ошибки имеют стабильный `code` и диагностическое `message`. Начальный набор
кодов: `invalid_request`, `unsupported_protocol_version`, `unknown_method`,
`invalid_params`, `kompas_not_running`, `kompas_api_error`,
`no_active_document`, `object_not_found`, `object_invalidated`,
`internal_error`. Клиент принимает решения по `code`, не разбирая текст
`message`. Добавление кодов и методов внутри версии 1 допускается;
изменение смысла существующих полей требует новой версии.

## Передача и порядок выполнения

Для Named Pipe одно сообщение — четырёхбайтовая беззнаковая длина JSON в
байтах (little-endian), затем ровно указанное число байт UTF-8. Ограничение
одного JSON-сообщения в версии 1 — 1 МиБ; пустое сообщение и превышение лимита
отвергаются до разбора JSON. Некорректный UTF-8 также отвергается. Порядок
байтов длины не зависит от порядка байтов хоста. Соединение обслуживает
последовательные запросы;
один ответ соответствует одному запросу. Bridge сериализует все обращения к
COM/KsAPI в своём STA-потоке и сохраняет порядок исполнения внутри соединения.

Bridge запускается командой:

```powershell
kompas_bridge.exe --pipe
```

Сервер создаёт `\\.\pipe\kompas-bridge`, принимает одного клиента и выполняет
его запросы последовательно. После отключения клиента COM-сессия не
пересоздаётся: bridge ожидает следующее соединение. Незавершённая операция
чтения или записи обрывается через 30 секунд. Pipe запрещает удалённых клиентов.
Именованный mutex с SID текущего пользователя не позволяет запустить второй
bridge в той же пользовательской сессии. Ctrl+C, Ctrl+Break, закрытие консоли и
завершение Windows инициируют остановку ожидания, после чего RAII освобождает
pipe, COM-объекты и STA.

Python-клиент `kompas_bridge_transport.NamedPipeClient` применяет тот же
30-секундный таймаут по умолчанию, проверяет `protocol_version` и соответствие
`id` ответа запросу. `close()` отключает только клиента и не завершает bridge.

Временный stdio-транспорт использует тот же JSON envelope, но другое framing:
одна строка UTF-8 JSON на запрос и одна строка UTF-8 JSON на ответ. Символы
перевода строки внутри JSON-строк экранируются. EOF завершает процесс; лимит
строки до завершающего перевода строки — 1 МиБ. Только ответы печатаются в
stdout, диагностические сообщения — в stderr. Если работающий КОМПАС не
найден при запуске, bridge остаётся в отключённом состоянии. При
невалидном запросе возвращается JSON-ошибка, после чего процесс продолжает
обслуживать следующие запросы.

## Сеанс и объектные handles

`document_id`, `part_id`, `sketch_id` и `feature_id` — непрозрачные строки,
выданные bridge. Python не конструирует их из имён или адресов COM-объектов.
Handle действует только в текущем процессе bridge и до освобождения объекта
или закрытия его документа. Смена активного документа сама по себе не делает
handle другого открытого документа недействительным. После перезапуска bridge
Core заново обнаруживает документы и объекты; в handles включён случайный
идентификатор bridge-сессии, поэтому старые handles не переиспользуются.
Запрос к неизвестному handle возвращает `object_not_found`, к недавно
освобождённому или инвалидированному — `object_invalidated`. Реестр хранит
не более 4096 tombstones; более старый handle снова считается неизвестным.
COM-ссылки остаются в bridge и освобождаются через RAII. При `disconnect`
все зарегистрированные handles инвалидируются до освобождения COM-сеанса.

`object.get_info` принимает `params: {"handle":"..."}` и возвращает
`handle`, `kind` (`document`, `part`, `sketch`, `feature`) и `document_id` для
дочернего объекта; для документа `document_id: null`. `object.release` с теми
же параметрами возвращает `{ "released": true }`. Освобождение document handle
инвалидирует все его дочерние handles, но не закрывает CAD-документ. При
закрытии документа через будущий `DocumentService` должен вызываться
`on_document_closed`, инвалидирующий документ и потомков.

Пока публичного метода, создающего handles из открытых документов, нет.
Закрытие документа вручную в GUI автоматически не отслеживается: это
потребует отдельного механизма синхронизации в следующем этапе.

Bridge при запуске использует политику `attach_only`; если открытого КОМПАСа
нет, процесс продолжает работать без подключения. `application.connect` без
параметров также использует `attach_only` и возвращает `kompas_not_running`,
если присоединиться не удалось. Создание процесса как побочный эффект
`application.status`, `document.get_active` или другой операции чтения
недопустимо.

## Первые методы

На текущем этапе исполняются три метода приложения:

- `application.status` с `params: {}` возвращает `connected`, `visible` и
  `kompas_version`. При отсутствии подключения последние два поля равны `null`.
  При подключении `visible` читается через API5 `GetVisible`, а числовые поля
  версии — через `ksGetSystemVersion`.
- `application.connect` принимает `params: {}` или
  `params: {"policy":"attach_only"}` (по умолчанию),
  `"attach_or_start"`, `"start_new"`. Возвращает тот же объект состояния.
  `attach_only` использует только активный COM-объект; `attach_or_start`
  активирует COM-сервер, лишь когда работающий объект не найден;
  `start_new` запрашивает новую COM-активацию без проверки ROT.
- `application.disconnect` принимает `params: {}` и освобождает ссылку bridge
  на приложение, не вызывая завершение КОМПАСа. После этого статус возвращает
  `connected: false`. COM-квартира bridge остаётся активной до выхода процесса.

Повторный `connect` с `attach_only` или `attach_or_start` при уже существующем
подключении возвращает текущее состояние; для `start_new` сначала требуется
`disconnect`. `CoCreateInstance` создаёт COM-объект, но отдельный процесс
КОМПАСа не гарантирует: сервер может использовать существующий процесс.

## Документные методы

Все методы используют общий JSON envelope версии 1. У каждого метода `params`
должен быть объектом; неизвестные поля отвергаются с `invalid_params`. Пути к
файлам передаются в UTF-8 и должны быть абсолютными. `document_id` и `part_id`
— непрозрачные идентификаторы одной bridge-сессии, не COM-указатели.

| Метод | Параметры | Результат |
| --- | --- | --- |
| `document.list` | `{}` | `{"documents": [DocumentInfo, ...]}` |
| `document.get_active` | `{}` | `DocumentInfo`; без активного документа — `no_active_document` |
| `document.create_3d` | `{"visible": true}`; `visible` по умолчанию `true` | `DocumentResult` |
| `document.open` | `file_path` (обязателен), `visible` (по умолчанию `true`), `read_only` (по умолчанию `false`) | `DocumentResult` |
| `document.activate` | `document_id` | `DocumentInfo` |
| `document.get_top_part` | `document_id` | `{"document_id": "...", "part_id": "..."}` |
| `document.save` | `document_id` | `DocumentInfo`; для нового файла сначала нужен `save_as` |
| `document.save_as` | `document_id`, `file_path`, `overwrite` (по умолчанию `false`) | `DocumentInfo`; существующий файл без `overwrite` отвергается |
| `document.close` | `document_id`, `discard_changes` (по умолчанию `false`) | `{"document_id": "...", "closed": true}`; изменённый документ без явного разрешения на потерю изменений не закрывается |

`DocumentInfo`: `document_id`, `document_type` (числовой тип SDK), `name`,
`file_path` (или `null`), `active`, `changed`, `read_only`.
`DocumentResult` расширяет `DocumentInfo` полями `part_id` (или `null`) и
`is_new`. `document.create_3d` создаёт деталь (`ksDocumentPart`). Открытие уже
открытого файла возвращает идентификатор существующего COM-документа, если
SDK возвращает тот же объект. Повторное чтение документа сохраняет handle.
Закрытие через bridge инвалидирует и документ, и его дочерние handles.

Ошибки COM возвращаются как `kompas_api_error`, отсутствие подключения как
`kompas_not_running`, неверные параметры как `invalid_params`, а устаревший
handle как `object_invalidated` или `object_not_found`.

Старые фикстуры `bridge.ping` удалены вместе с демонстрационным CLI.
