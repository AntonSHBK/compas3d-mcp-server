# Архитектура kompas3d-mcp-server

## Назначение и границы

Проект предоставляет ИИ-агенту управляемый доступ к КОМПАС-3D под Windows.
Целевая цепочка вызова:

```text
Агент / MCP-клиент
  → kompas_mcp (Python)
  → kompas_core (Python)
  → kompas_bridge_transport (Python)
  → локальный Windows Named Pipe
  → kompas_bridge (C++)
  → COM / API5 и API7
  → КОМПАС-3D
```

| Компонент | Ответственность |
| --- | --- |
| `kompas_mcp` | MCP transport, объявления инструментов, проверка входов и передача результатов агенту. Инструменты остаются тонкими и вызывают Core. |
| `kompas_core` | Независимый от MCP объектный CAD API: документы, детали, эскизы, операции, семантические селекторы, измерения и валидация сценариев. Использует только Python-клиент bridge. |
| `kompas_bridge_transport` | Запуск или подключение к bridge, сериализация внутреннего протокола, Named Pipe, таймауты и преобразование ошибок транспорта. Не содержит CAD-семантики. |
| `kompas_bridge` | Постоянный C++ процесс: COM/KsAPI, жизненный цикл сеанса, низкоуровневые CAD-вызовы, реестр объектных handles, диспетчер запросов и IPC. Не реализует MCP и не принимает произвольный код. |
| КОМПАС-3D | Внешнее CAD-приложение, хранящее открытые документы и выполняющее операции над моделью. |

Python не получает COM-указатели: bridge возвращает непрозрачные идентификаторы
документов и объектов. Core превращает низкоуровневые операции bridge в удобные
сценарии, например создание эскиза и выдавливания. MCP предоставляет эти
возможности агенту, но не содержит последовательностей вызовов SDK.

## Поток команды и состояние

Агент запрашивает состояние модели, планирует изменение, отправляет действие и
проверяет получившийся результат. MCP вызывает Core; Core вызывает один или
несколько низкоуровневых методов bridge через Python transport. Bridge
исполняет их последовательно в КОМПАСе и возвращает результаты или
структурированные ошибки. Изображение модели, когда появится его получение,
проходит обратно через Core и MCP к агенту для визуальной проверки.

Целевой bridge — долгоживущий процесс. Он сохраняет COM-сеанс и реестр handles
между запросами, чтобы продолжать работу в открытом документе и переключаться
между файлами. Все обращения к КОМПАСу выполняются в одном STA COM-потоке;
потоки IPC не вызывают COM напрямую. Закрытие документа инвалидирует связанные
с ним handles; после перезапуска bridge старые handles недействительны.

По умолчанию bridge подключается только к уже работающему КОМПАСу
(`attach_only`). Запуск нового экземпляра допускается лишь при явно выбранной
политике подключения. Операции, способные затронуть открытые пользовательские
документы, должны иметь явные параметры и возвращать наблюдаемый результат.

## Контракт между Python и C++

Между `kompas_bridge_transport` и `kompas_bridge` используется локальный
версионируемый JSON-протокол поверх Named Pipe. Формат запросов, ответов,
ошибок и handles описан в [bridge_protocol.md](bridge_protocol.md). MCP поверх
него не проксирует произвольные вызовы COM и не принимает C++/KsAPI-код для
выполнения. Bridge публикует только заранее определённые низкоуровневые методы.

## Текущее состояние и переход

`kompas_bridge.exe --stdio` обслуживает последовательные JSON-запросы в
одном процессе и одном STA COM-сеансе. Реализованы `application.status`,
`application.connect` и `application.disconnect`; демонстрационные CLI-команды
удалены. При запуске bridge использует `attach_only` и не запускает КОМПАС
автоматически. Явная команда подключения поддерживает три политики. Внутри
bridge работает `ObjectRegistry` с COM-ссылками и строковыми handles; публичны
`object.get_info` и `object.release`. Named Pipe и методы выдачи handles для
открытых документов ещё не реализованы.
Каталоги
`python/kompas_core` и `python/kompas_bridge_transport` созданы, но их
публичный API пока не реализован; `kompas_mcp` остаётся каркасом.

`src/kompas_plugin` — отдельный эксперимент с плагином КОМПАСа. Он не является
точкой входа MCP и не заменяет внешний C++ bridge.
