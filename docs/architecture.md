# Архитектура

## Назначение

`kompas3d-mcp-server` предоставляет агентам стандартизированный MCP-интерфейс
для управления КОМПАС-3D под Windows. Цель — постепенно развить набор
надёжных CAD-инструментов: от 2D-документов и базовой геометрии до 3D-операций,
экспорта и составных сценариев оформления.

Проект разделён на Python MCP-слой и нативный C++ bridge. Такое разделение
оставляет агентную и протокольную логику в Python, а всю специфику Windows
COM/KsAPI — в изолированном процессе.

## Компоненты

| Компонент | Ответственность |
| --- | --- |
| `kompas_mcp` | Точка входа Python, MCP transport, tool declarations, валидация, сценарии, конфигурация и логи. |
| `kompas_bridge` | Локальный C++ процесс: Named Pipe, управление сеансом КОМПАСа, очередь операций и вызовы COM/KsAPI. |
| КОМПАС-3D | Внешнее Windows CAD-приложение, выполняющее фактические операции над документами. |

Текущее состояние: оба компонента существуют как каркасы. MCP transport,
Named Pipe, подключение к SDK и реальные CAD-команды пока отсутствуют.

## Поток команды

```text
Агент / MCP-клиент
        │ MCP
        ▼
kompas_mcp.tools
        │
        ▼
kompas_mcp.services
        │ версионируемый JSON по локальному Named Pipe
        ▼
kompas_bridge
        │ COM / KsAPI, последовательная очередь операций
        ▼
КОМПАС-3D
```

Python не получает и не передаёт COM-объекты. Bridge не реализует MCP и не
содержит агентной логики. Это позволяет развивать оба слоя независимо и
перезапускать bridge при сбоях нативной интеграции.

## Границы слоёв

`tools` описывает внешний MCP API и остаётся тонким. `services` реализует
прикладные сценарии и вызывает клиента bridge. `bridge` в Python отвечает за
процесс и внутренний протокол, но не за SDK. В C++ доступ к SDK должен быть
сконцентрирован в коде сеанса и обработчиках команд.

Внутренний контракт Python ↔ C++ — JSON с версией протокола, идентификатором
запроса, именем команды, аргументами и структурированным результатом или
ошибкой. Примеры контракта хранятся в `tests/kompas_mcp/data/bridge/`.

## Жизненный цикл и конкуренция

Python MCP-процесс запускается клиентом. Он запускает или подключается к
`kompas_bridge`; bridge, в свою очередь, создаёт либо присоединяет сеанс
КОМПАСа. Операции одного сеанса должны исполняться последовательно в
совместимом с COM потоке. Параллельные запросы не должны одновременно менять
активный CAD-документ.

## Первый вертикальный срез

1. `bridge.ping` и диагностическая команда;
2. запуск или подключение к КОМПАС-3D;
3. создание 2D-документа;
4. создание линии;
5. сохранение документа.

Каждая следующая возможность проходит тот же путь: C++ bridge-команда,
Python-клиент, service, MCP tool, unit-тесты и JSON-примеры протокола.

## Тестирование

Python unit-тесты используют `pytest` и не зависят от установленного
КОМПАСа. Общие фикстуры находятся в `tests/kompas_mcp/fixtures/`, статичные
данные протокола — в `data/`, а управляемые замены транспорта — в `fakes/`.

Интеграционные сценарии помечаются `@pytest.mark.integration` и запускаются
отдельно на Windows с собранным bridge и установленным КОМПАСом. C++ тесты
будут добавляться в `tests/kompas_bridge/` по мере реализации bridge.
