# C++ Development

## Общие принципы

При разработке на C++ следовать следующим принципам:

* Использовать современный C++. По умолчанию ориентироваться на C++20. Допускается C++17, если это требуется существующим проектом или зависимостями.
* Предпочитать RAII ручному управлению ресурсами.
* Не использовать `new` и `delete` в прикладном коде без объективной необходимости.
* Использовать стандартную библиотеку C++, если она предоставляет подходящее решение. Не создавать собственные аналоги стандартных контейнеров, алгоритмов и базовых утилит без необходимости.
* Минимизировать глобальное состояние.
* Минимизировать изменяемое состояние (`mutable state`) и область его распространения.
* Использовать строгую типизацию и явно выражать семантику данных через типы.
* Не допускать undefined behavior.
* Не использовать C-style cast. Использовать соответствующие C++ casts: `static_cast`, `dynamic_cast`, `const_cast`, `reinterpret_cast`.
* Все ошибки должны обрабатываться явно. Не игнорировать ошибки и исключения без обоснованной причины.
* Предпочитать простой и читаемый код чрезмерно абстрактным или усложнённым решениям.
* Не добавлять новые зависимости, если задача может быть разумно решена средствами стандартной библиотеки или уже используемых библиотек проекта.

## Стандарт языка

По умолчанию использовать C++20:

```cmake
target_compile_features(target_name PUBLIC cxx_std_20)
```

Если существующий проект использует C++17, сохранять текущий стандарт, если задача не требует его изменения.

## Структура проекта

Для новых C++-проектов использовать следующую базовую структуру:

```text
project/
├── CMakeLists.txt
├── cmake/
├── include/
│   └── project/
├── src/
├── tests/
├── examples/
├── docs/
└── third_party/
```

## Форматирование

Использовать Google C++ Style как базовый стиль форматирования.

Основные правила:

* Отступ: 2 пробела.
* Не использовать табуляцию для отступов.
* Максимальная рекомендуемая длина строки: 100 символов.
* Открывающую фигурную скобку размещать на той же строке, что и управляющая конструкция, функция, класс или namespace.
* Всегда использовать фигурные скобки для `if`, `else`, `for`, `while` и других управляющих конструкций, даже если тело состоит из одной инструкции.
* Форматирование должно быть совместимо с `clang-format`.

## Именование

Использовать следующие соглашения.

### Классы и структуры

Использовать `PascalCase`.

```cpp
class KompasBridge;
class DocumentManager;

struct Point3D;
struct ConnectionConfig;
```

### Методы и функции

Использовать `snake_case`.

```cpp
connect_to_kompas();
create_document();
get_active_document();
calculate_area();
```

Имена функций и методов должны отражать выполняемое действие.

Для методов, возвращающих логическое значение, использовать понятные имена:

```cpp
is_connected();
has_document();
can_execute();
should_retry();
```

Избегать неопределённых имён:

```cpp
process();
handle();
do_work();
func();
```

если из контекста невозможно однозначно понять назначение функции.

### Переменные

Использовать `camelCase`.

```cpp
int retryCount;
double targetAltitude;
std::string documentName;
```

### Константы

Использовать Google-style с префиксом `k` и `PascalCase`.

```cpp
constexpr int kMaxConnections = 10;
constexpr double kDefaultScale = 1.0;
constexpr std::chrono::seconds kConnectionTimeout{5};
```

## Namespace

Использовать lowercase или `snake_case` для namespace.

```cpp
namespace kompas {

class Bridge {
};

}  // namespace kompas
```

Для вложенных namespace использовать синтаксис C++17:

```cpp
namespace artis::kompas::geometry {

class PointConverter {
};

}  // namespace artis::kompas::geometry
```

Не использовать:

```cpp
using namespace std;
```

особенно в заголовочных файлах.

## Имена файлов

Использовать `snake_case`.

Примеры:

```text
kompas_bridge.hpp
kompas_bridge.cpp
document_manager.hpp
document_manager.cpp
geometry_converter.hpp
geometry_converter.cpp
```

Имя `.cpp` и соответствующего `.hpp` файла должно совпадать.

## Заголовочные файлы

Для C++-заголовков использовать расширение `.hpp`.

Для защиты от повторного включения использовать:

```cpp
#pragma once
```

## Порядок include

В `.cpp` файлах использовать следующий порядок:

1. Заголовочный файл текущей реализации.
2. Заголовки стандартной библиотеки.
3. Заголовки сторонних библиотек.
4. Внутренние заголовки проекта.

Между группами оставлять пустую строку.

## Исключения и обработка ошибок

Использовать исключения для ошибок, которые невозможно корректно обработать непосредственно в текущем месте выполнения.

Пример:

```cpp
throw std::runtime_error("Failed to connect to KOMPAS");
```

## Сообщения об ошибках

Сообщение об ошибке должно содержать контекст, необходимый для диагностики проблемы.

По возможности указывать:

* выполняемую операцию;
* объект, к которому относится ошибка;
* путь к файлу;
* идентификатор сущности;
* код ошибки внешнего API;
* другое диагностически значимое значение.

## Комментарии

Комментарии в исходном коде писать на русском языке.

Не добавлять комментарии к очевидным операциям внутри метода.

Обычные комментарии использовать только в случаях, когда необходимо объяснить неочевидное архитектурное решение, ограничение внешнего API или особенность реализации.

Основную документацию методов и классов оформлять через Doxygen.

Не использовать комментарии для компенсации плохо именованного или чрезмерно сложного кода.

## Doxygen

Для документации публичных классов, методов и функций использовать Doxygen.


## CMake

Можно включить рекомендации:

```cmake
target_compile_features(core PUBLIC cxx_std_20)
```

Предпочитать target-based CMake:

```cmake
target_link_libraries(...)
target_include_directories(...)
target_compile_definitions(...)
```
